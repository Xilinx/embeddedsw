s32 XAsu_KmGetMldsaKeyLengths ( u8  ParamSet,
u32 *  PubKeyLenPtr,
u32 *  PrivKeyLenPtr 
)

This function resolves the ML-DSA public and private key lengths of a parameter set.

Unlike the other algorithms, an ML-DSA key pair has no single "key length": the two halves differ in size and neither is derivable from the other, so both are returned from the parameter set carried in the key attributes.

Parameters
ParamSetML-DSA parameter set (see XAsu_MldsaParamSet).
PubKeyLenPtrPointer to the output public key length in bytes.
PrivKeyLenPtrPointer to the output private key length in bytes.
Returns
  • XST_SUCCESS, if the parameter set is supported and both lengths are returned.
  • XST_FAILURE, if a pointer is NULL or the parameter set is unsupported.

s32 XAsu_KmValidateAesKeySplitUseCase ( u8  KeyType,
u8  KeyUseCase 
)

This function validates that an AES key does not combine the key split use case with any other use case.

The key type is taken as a parameter rather than read from the key metadata, because the Generate Key APIs pass their own key type. For any other key type the function returns success, since the key split use case bit is reserved there.

Parameters
KeyTypeKey type identifier. May include the wrapped-key bit (XASU_KM_KEYTYPE_WRAPPED_BIT_MASK), which is masked out before comparing against the sub-vault identifier.
KeyUseCaseKey use case value from the key metadata.
Returns
  • XST_SUCCESS, if the key use case is valid for the given key type.
  • XST_FAILURE, if the key use case is invalid.

For an AES key the key split use case is exclusive. A key which also carries another AES use case is usable as a key in its own right, which defeats the purpose of splitting it.

References XASU_AES_SUBVAULT_ID, XASU_KEYMANAGER_AES_KEY_SPLIT_USE_CASE, and XASU_KM_KEYTYPE_WRAPPED_BIT_MASK.

Referenced by XAsu_KmValidateParams(), XAsu_KmValidateXorKeyParams(), and XAsu_ProvisionValidateStoreKeyMetadata().

s32 XAsu_KmValidateKeyAddrNdKeyId ( u64  KeyCompAddr,
u32  KeyCompLen,
u64  KeyId 
)

This function validates that exactly one of KeyCompAddr or KeyId is provided, and that a vault sourced component carries no length.

It applies to anything the key vault holds, a key or an IV. KeyId is u64 so the same helper can test either a composite vault KeyId or a full 64-bit KeyIdAddr without truncating high addresses.

Parameters
KeyCompAddrAddress of the key or IV component, 0 when it is taken from the key vault.
KeyCompLenLength of the key or IV component buffer in bytes. A component whose length the caller does not supply passes 0.
KeyIdComposite vault key/IV identifier, or a destination KeyIdAddr when used by generate-parameter validation.
Returns
  • XST_SUCCESS, if exactly one of (KeyCompAddr, KeyId) is non-zero and a vault sourced component carries a zero length.
  • XST_FAILURE, if both are zero (no source) or both are non-zero (ambiguous source), or if a vault sourced component carries a non-zero length.

Reject if both are zero (no source) or both are non-zero (ambiguous source).

A component held in the key vault is not passed by the caller and the firmware takes its length from the stored metadata, so the request must leave the length at zero. Reject a left over length here, where the caller learns it supplied an invalid parameter, rather than letting the server range check a buffer at address zero.

s32 XAsu_KmValidateKeyAttributes ( u8  KeyType,
u8  KeyAttributes 
)

This function validates the key type and its key attributes field.

It rejects a key type that has no storable sub-vault (invalid or unknown values) and then validates the key attributes against the key type.

Parameters
KeyTypeKey type identifier. May include the wrapped-key bit (XASU_KM_KEYTYPE_WRAPPED_BIT_MASK), which is masked out before comparing against the sub-vault identifier.
KeyAttributesKey attributes value from the key metadata.
Returns
  • XST_SUCCESS, if the key attributes are valid for the given key type.
  • XST_FAILURE, if the key attributes are invalid or the key type has no storable sub-vault.

Reject a key type that does not map to a storable sub-vault. The sub-vault IDs run without gaps from XASU_AES_SUBVAULT_ID up to XASU_INVALID_SUBVAULT_ID, so a single range check covers every storable type. Invalid sub-vaults are excluded by design; no caller of this helper stores or generates them.

For an RSA private key, the key attributes encode the private key format (prime/totient presence) and must not exceed the maximum supported value.

References XASU_INVALID_SUBVAULT_ID, XASU_KM_KEYTYPE_WRAPPED_BIT_MASK, XASU_KM_RSA_PVT_ATTR_MAX, and XASU_RSA_PVT_SUBVAULT_ID.

s32 XAsu_KmValidateParams ( const XAsu_KeyManagerParams *  KmParamsPtr,
u8  ValidationFlow,
u8  KeyType,
u32  MinimumKeyObjectLen 
)

Validate key manager Generate and Store requests.

Parameters
KmParamsPtrPointer to XAsu_KeyManagerParams structure that holds the input parameters for Key manager APIs.
ValidationFlowValidation flow selector (XASU_KM_VALIDATE_FLOW_INVALID is rejected):
  • XASU_KM_VALIDATE_FLOW_GENERATE: exactly one of KeyObjectAddr or KeyIdAddr is set; when exporting to client memory, KeyObjectLen must cover the larger of KeyMetadata.Length and MinimumKeyObjectLen; when storing in the vault, KeyMetadata is validated and the key type in CompositeKeyId must equal KeyType.
  • XASU_KM_VALIDATE_FLOW_STORE: KeyObjectAddr, KeyIdAddr, and KeyObjectLen are mandatory; KeyMetadata, key attributes, key type, and plain/wrapped length rules are checked. Both flows check that the key type is a valid sub-vault ID and apply the AES key split use-case rule.
KeyTypeGenerate flow key type: the sub-vault ID for AES, IV and KDF/HMAC keys, or the private sub-vault ID for RSA, ECC, ML-DSA and ML-KEM key pairs. It must be a valid sub-vault ID without the wrapped-key bit. It selects the key length rule for AES, IV, KDF/HMAC and RSA, the RSA attribute rule, and the ECC curve check. ML-DSA and ML-KEM parameters are checked by their algorithm-specific validators. Ignored for the Store flow, where the key type is obtained from CompositeKeyId.
MinimumKeyObjectLenSize of the complete exported object for the Generate flow. When the exported object is only the key bytes, pass KeyMetadata.Length; 0U has the same effect. Ignored when the generated key is stored in the vault and for the Store flow.
Returns
  • XST_SUCCESS, if input validation is successful.
  • XST_FAILURE, if input validation fails.

A key stored in the vault must carry the API's key type in CompositeKeyId.

A Generate key type must not carry the wrapped-key bit, so it is not masked.

Store API requires both input key buffer and output key ID address.

Checks common to both flows.

Check the ECC curve and its private-key length in the shared generate path.

An export buffer must hold the larger of the key and the complete exported object. AES, IV and KDF/HMAC export only the key, so the key length is that size. A key pair passes the object size, which is already at least the key length.

Plain Store Key input size depends on key type (RSA/ECC public objects are larger than KeyMetadata.Length alone). Require KeyObjectLen to cover the bytes the store path will consume from KeyObjectAddr.

This function validates the input parameters for combining two AES key splits using XOR.

The key type of the input key splits and the length of the combined key are validated by the server against the stored key splits.

Parameters

Returns

  • XST_FAILURE, if any input parameter is invalid.

Validate input parameters.

Validate that both input key IDs are provided.

The address for the output key ID is required when the destination slot is auto-assigned, and shall not be supplied when the caller selects the slot, since the composite key ID is then already known to the caller.

Reject identical input key IDs. A key XORed with itself yields an all zero key, so allowing this would let the caller install a known key of its choosing.

The combined key must not overwrite either input key split.

Key splitting is defined for AES keys only. The key slot may be zero, which requests an auto-assigned slot.
