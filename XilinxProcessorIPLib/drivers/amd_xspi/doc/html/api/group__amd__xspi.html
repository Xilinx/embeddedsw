Interrupt Enable/Status/Event Register bit definitions

The same bit positions are used by all three registers, but they do not behave alike.

AMD_XSPI_ISR reports each condition as a live level, independently of what AMD_XSPI_IER enables, so it can be polled directly and needs no acknowledgement. AMD_XSPI_INT_EVT latches an event only if the matching IER bit was set when the condition fired, and holds it until it is written back.

The polled paths rely on the live behavior. They test AMD_XSPI_ISR once per message without clearing anything between messages. That is only correct because a bit there tracks the current condition rather than remaining set from an earlier transaction.

#define AMD_XSPI_FIFO_SPIN_COUNT   256U

Bound on how long either direction waits for the FIFO to become workable: for a read, to report data; for a write, to report room.

The first AMD_XSPI_FIFO_SPIN_COUNT polls run back to back with no delay.

Being slow costs no data in either direction. The core stops the clock when the RX FIFO fills and waits when the TX FIFO runs dry. But it does spend the only budget that matters. Chip select cannot stay low past tCSM, 4 us on this part, and the core raises a transaction error when it does. What the FIFO is waiting on arrives within a clock or two, so the wait must not put a sleep in front of it.

Once those polls are spent, the transaction has outlived its tCSM budget and the core has already failed it. So nothing is gained by continuing to spin, and the remaining polls sleep. That costs the working case nothing. The timeout is then a wall clock bound of about AMD_XSPI_FIFO_SLEEP_COUNT microseconds. It is not a spin count whose real duration depends on the CPU and on AXI latency.

void AmdXspi_DrainRxFifo ( AmdXspi *  InstancePtr,
const AmdXspi_Msg *  Msg,
u8  WaitForAll 
)

Moves receive data from the RX FIFO into the message buffer.

Progress is accumulated in InstancePtr->MsgRxCnt. So a read larger than the FIFO can be assembled across successive fill-level interrupts. It does not have to be resident all at once when the transaction completes.

WaitForAll says what an empty FIFO means. Part way through a transaction it means the core has not produced the next entry yet, and returning is right. More fill-level interrupts are coming. Blocking in the handler for data the bus has not carried would spend the tCSM budget of the transaction that is still running.

At completion there are no further interrupts to wait for, so the same reading has to be retried. The core signals the transaction complete as the last entries reach the FIFO. The occupancy count crosses into this clock domain a little behind them. So a drain that starts the moment the interrupt arrives can find the FIFO reporting empty with data still landing. Giving up on that first reading loses the tail of the burst and is reported to the caller as a receive overrun.

The retry only ever spins. It runs in interrupt context, and by the time it is reached the bus has already delivered the data. So the wait is the handful of cycles the count takes to catch up, rather than anything bounded by the bus clock.

[in,out]InstancePtrPointer to the AmdXspi instance.
[in]MsgMessage whose receive buffer is being filled.
[in]WaitForAll0 to take only what is present and return, or 1 to wait out a late occupancy count until the message is satisfied.

s32 AmdXspi_RecvData ( AmdXspi *  InstancePtr,
u8 *  DataBuf,
u32  NumBytes 
)

Receives data bytes from the Receive Register.

The payload can be larger than the FIFO, since a Lite read may ask for up to AMD_XSPI_MAX_DATA_BYTES while C_FIFO_DEPTH goes as low as 16 entries. So the data is collected over as many passes as it takes. Each pass waits on RX_EMPTY for data to appear and then drains the number of entries the core reports. That keeps the wait to one register read per poll. It still lets a whole burst be taken without re-testing the FIFO per entry.

A failed transaction is not detected here and is left to run the wait out. So a read that the core has faulted costs the full timeout before it is reported.

AmdXspi_LiteRead(), the only caller, checks the instance, the ready state and the receive buffer, so nothing is rechecked.

void AmdXspi_Reset ( AmdXspi *  InstancePtr)

Resets the AXI XSPI controller.

The core is left disabled, since writing SOFT_RESET returns every control bit to its default. Enabling it is the caller's to do, which for the driver means AmdXspi_CfgInitialize(). Anything the application configured through the option functions is returned to its default and has to be set again.

This can reach past the controller. The core passes the soft reset through to its optional resetn output. So on a design built with that output wired, the attached memory is hardware reset too.

For a HyperRAM, that returns its configuration registers, including the initial latency, to their defaults. It also costs the contents of the array, which the datasheet says to treat as lost. Anything recovering an error through AmdXspi_Abort() inherits that.

Both callers check the instance beforehand. The ready state deliberately is not checked, since AmdXspi_CfgInitialize() resets the core before marking the instance ready.

void AmdXspi_StartMessage ( AmdXspi *  InstancePtr,
const AmdXspi_Msg *  Msg 
)

Starts a single message on the bus.

The message comprises the instruction and command/address, plus transmit data for a write.

This reuses the existing low-level building blocks (AmdXspi_SendInstruction/AmdXspi_SendCmdAddr/AmdXspi_FillTxFifo). It is used both by AmdXspi_InterruptTransfer (to launch the first message) and by AmdXspi_InterruptHandler (to launch each subsequent message on completion).

Nothing here blocks, which is what makes the second of those callers safe.

For a read, the interrupt handler drains receive data as the RX FIFO fills and again at completion. This function only issues the transaction.

The instance, the message and the ready state are checked by both callers. So what is checked here is the message content. Neither of them inspects it, and this function is the first to act on it.
