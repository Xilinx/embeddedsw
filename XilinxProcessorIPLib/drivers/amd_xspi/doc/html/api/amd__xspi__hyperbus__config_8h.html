amd_xspi_hyperbus_config.h File Reference

Overview

Defines the HyperBus device table for the AXI XSPI examples.

This file contains the HyperBus device configuration table and the related defines. It should be included by the AXI XSPI examples and compiled along with them (*.c). This follows the way xqspipsu_flash_config.h is used by the QSPIPSU examples.

This file supports HyperRAM over HyperBus. The table and its accessors are arranged so that further HyperRAM parts, from Infineon or any other vendor, are added as data alone.

Why a device table The AXI XSPI driver is protocol-agnostic: in AXI-Lite mode it only moves Command/Address and data bytes. Everything that is device specific therefore lives in the application.

Only the parameters that NO register reports belong here. Anything a device can be asked about is read from it at runtime:

Read from the device, never tabulated: Manufacturer ID and geometry from IR0, device type from IR1, and the current latency/burst/fixed-latency from CR0. Density, array rows and the address limit are arithmetic on the IR0 row and column bit counts.

Tabulated here, because no register conveys it:

  • What a latency code MEANS in clocks, and the power-on default
  • What a burst code MEANS in bytes
  • Power-up time, tCSM and the refresh interval
  • A human readable part name

Because geometry is never stored, one entry covers every density in a family.

The bootstrap problem A HyperBus read uses the device's current initial latency - including the read that discovers what the device is. Unlike SFDP, which NOR flash exposes through a command with a spec-fixed dummy count, HyperBus offers no known-latency entry point.

The host does not choose this number freely, it has to reproduce the one the device is programmed to. Per datasheet 002-24692 section 4.2, once the latency clocks named by CR0[7:4] have elapsed, "the memory starts to simultaneously transition the RWDS and output the target data". It keeps streaming for as long as the clock runs.

The device never waits for the host. Counting too few clocks samples before the data arrives. Counting too many samples past the words that have already gone by. Both give wrong data.

The identifying read is possible because CR0[7:4] comes out of reset at the family maximum. The datasheet states this value, so the integrator can supply it before any register has been read. Section 6.3.2.2 adds that this reset value satisfies tACC all the way to the part's top frequency. So no bus clock a design can legally run needs it lowered first. Lowering it afterwards is a throughput optimization, not a requirement, and the frequency the design runs at never enters into the identifying read.

That value is not taken from this table, because the table cannot be consulted until the device is known. Each example names it as HYPERRAM_DEFAULT_LATENCY_CLOCKS and the integrator sets it for the part fitted to the board. The table does not record it per entry.

The HyperBus specification fixes the reset value at 7 clocks for every part. A successful identifying read is itself proof that the configured value matched the device. So a per entry copy could only ever disagree by being stale.

Getting it wrong in the short direction is worse than wrong data. Measurement on an S27KL0642 shows every later transaction returning zeros. Neither aborting the transfer nor cycling the controller brings the part back. Chip select held past tCSM starves the array of refresh, and only RESET# or a power cycle clears it.

A part whose reset default is unknown therefore cannot be identified by trial. A wrong guess is unrecoverable in software, and there is no second attempt to spend. Hence the value is configured rather than searched for.

C_TGT_LATENCY is no help here, which is why neither the driver nor these examples read it. A Lite mode design cannot set it, so it stays at the IP default of 4. That value is outside the parameter's own documented range of 7, and no supported device uses it at power-on. The same applies to C_TGT_MEM_SIZE and C_TGT_BURST_LENGTH: geometry, latency and burst length come from the identified device, not from the design.

Adding a new device Append one entry to HyperBus_Config_Table[]. Nothing else needs to change, because the entry holds only the identifiers, a name and tCSM. No latency or burst code is decoded, so nothing in it is a per part encoding. A board fitted with a part whose reset latency differs from the one the example is set for needs HYPERRAM_DEFAULT_LATENCY_CLOCKS changed to match. The bootstrap note above explains why trying each in turn instead is not an option on a board that cannot assert RESET# between attempts.
